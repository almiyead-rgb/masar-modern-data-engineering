<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>1. Give each tool a clear role</h2><p>Spark executes SQL; Delta manages table transactions; dbt organizes SQL models, dependencies, tests and documentation through its Spark adapter. <code>source()</code> refers to an existing source table. <code>ref()</code> links one model to another. Neither function ingests the raw CSV.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>١. حدد وظيفة كل أداة</h2><p>ينفّذ Spark استعلامات SQL، وتدير Delta معاملات الجداول، وينظم dbt نماذج SQL واعتمادها واختباراتها وتوثيقها عبر موصل Spark. تشير <code>source()</code> إلى جدول مصدر موجود، وتربط <code>ref()</code> نموذجًا بآخر. لا تجلب أي من الدالتين ملف CSV الخام.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>2. Follow the six-model graph</h2><p><code>stg_trips</code>: typed trip receipts.<br><code>stg_drivers</code>: unique, standardized drivers.<br><code>stg_gps</code>: parsed and validated events.<br><code>int_trip_candidates</code>: one validated candidate per trip.<br><code>silver_trips</code>: incremental Delta table.<br><code>mart_city_daily</code>: one summary per city and local trip date.</p><p>Trips and drivers feed the candidate model, then Silver, then the city/day summary. GPS is a separately tested branch; raw events are not joined into trip fares. Explore <a href="dbt/models/">models/</a> without copying the same SQL into multiple files.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٢. تتبع النماذج الستة</h2><p><code>stg_trips</code>: نسخ الرحلات بعد تحويل أنواعها.<br><code>stg_drivers</code>: سائقون موحدون بمفاتيح فريدة.<br><code>stg_gps</code>: أحداث مواقع مفككة ومفحوصة.<br><code>int_trip_candidates</code>: سجل مرشح صالح لكل رحلة.<br><code>silver_trips</code>: جدول Delta تزايدي.<br><code>mart_city_daily</code>: ملخص لكل مدينة وتاريخ رحلة محلي.</p><p>تغذي الرحلات والسائقون نموذج السجلات المرشحة، ثم Silver، ثم ملخص المدينة واليوم. المواقع فرع مستقل مفحوص؛ لا تُربط أحداثها الخام بأجور الرحلات. استكشف <a href="dbt/models/">models/</a> دون نسخ SQL نفسه في ملفات متعددة.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>3. Use the notebook runner</h2><p>After 03a and 03b, run the dbt cell in the same daily notebook. <code>run_dbt_lab(ROOT)</code> creates an isolated workspace, copies actual Day 1 Delta snapshots while preserving their receipt timestamps, and invokes dbt in one local Spark session. It needs no cloud account, token or Thrift server.</p><p>Do not run <code>dbt build</code> in a separate process for this setup: its in-memory catalog would not contain the registered source tables. Generated files stay under the printed dbt workspace, not in the tracked <code>day02/dbt/</code> project or your continuing Silver table.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٣. استخدم مشغّل الدفتر</h2><p>بعد 03a و03b، شغّل خلية dbt في دفتر اليوم نفسه. تُنشئ <code>run_dbt_lab(ROOT)</code> مساحة معزولة، وتنسخ لقطات Delta الفعلية لليوم الأول مع الحفاظ على توقيتات استقبالها، ثم تستدعي dbt في جلسة Spark محلية واحدة. لا تحتاج إلى حساب سحابي أو رمز وصول أو خادم Thrift.</p><p>لا تشغّل <code>dbt build</code> بعملية منفصلة في هذا الإعداد؛ فلن يحتوي كتالوجها الموجود في الذاكرة على جداول المصدر المسجلة. تبقى الملفات المولدة داخل مساحة dbt المطبوعة، لا داخل مشروع <code>day02/dbt/</code> المتتبع أو جدول Silver الذي ستكمل عليه.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>4. Validate before merging</h2><p>Each phase builds staging, runs domain/relationship/conflict checks, checks source freshness, builds the remaining models and tests, then reads Delta back. A failed pre-merge check stops the phase. A failed later test does not turn multiple models into one rolled-back transaction.</p><p>Read <a href="dbt/models/schema.yml">schema.yml</a> for key and null tests, and <a href="dbt/tests/">tests/</a> for seven SQL tests. Trip receipts intentionally repeat <code>trip_id</code>; driver keys, candidate keys and Silver trip keys must be unique. A <code>unique_key</code> configuration is not itself a uniqueness test. [D2-3, D2-6, D2-8]</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٤. افحص قبل الدمج</h2><p>تبني كل مرحلة التهيئة، وتفحص القيم والعلاقات والتعارض، وتتحقق من حداثة المصدر، ثم تبني النماذج الأخرى واختباراتها وتعيد قراءة Delta. يوقف فشل الفحص السابق للدمج المرحلة. أما فشل اختبار لاحق فلا يعني التراجع عن جميع النماذج بوصفها معاملة واحدة.</p><p>اقرأ <a href="dbt/models/schema.yml">schema.yml</a> لاختبارات المفاتيح والقيم المفقودة، و<a href="dbt/tests/">tests/</a> لاختبارات SQL السبعة. تتكرر <code>trip_id</code> عمدًا في نسخ الاستقبال، لكن مفاتيح السائقين والسجلات المرشحة ورحلات Silver يجب أن تكون فريدة. إعداد <code>unique_key</code> ليس اختبار تفرد بحد ذاته. [D2-3، D2-6، D2-8]</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>5. Look back on arrival time</h2><p><a href="dbt/models/silver/silver_trips.sql">silver_trips.sql</a> filters candidates using <code>_ingested_at</code> relative to the latest target timestamp minus three days. It does not filter by the trip event date. A historical trip arriving now can therefore be included.</p><p>The candidate model first ranks the complete small source history, after conflict checks, so a replayed older revision cannot replace a newer one. This prioritizes correctness for the small fixture; it is not a claim of optimized scanning at production scale. [D2-6]</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٥. استخدم وقت الوصول لنافذة المراجعة</h2><p>يصفّي <a href="dbt/models/silver/silver_trips.sql">silver_trips.sql</a> السجلات المرشحة باستخدام <code>_ingested_at</code> مقارنةً بأحدث توقيت في الهدف ناقص ثلاثة أيام، وليس بتاريخ وقوع الرحلة. لذلك يمكن إدراج رحلة تاريخية تصل الآن.</p><p>يرتب نموذج السجلات المرشحة كامل السجل الصغير بعد فحص التعارض، حتى لا تستبدل إعادة إرسال مراجعة قديمة مراجعةً أحدث. تعطي هذه الطريقة الأولوية لصحة البيانات الصغيرة؛ ولا تدّعي تقليل القراءة في أحمال إنتاج كبيرة. [D2-6]</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>6. Distinguish backfill from a full rebuild</h2><p>The supplied late-trip batch is the required backfill exercise: retain the older business date and count each trip once. <code>--reprocess-all</code> is an optional runner switch that removes the ingestion-window filter while retaining conflict and revision rules. It covers available history only; it cannot recreate records absent from the sources.</p><p>It is not <code>--full-refresh</code> and does not delete previous work. Leave <code>--include-correction</code> off during Day 2; that optional validation belongs to a later stage. No extra submission is required.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٦. ميّز الاستكمال التاريخي من إعادة البناء</h2><p>الدفعة المتأخرة المرفقة هي تمرين استكمال البيانات السابقة المطلوب: تحتفظ بتاريخ أعمالها الأقدم وتُحتسب كل رحلة مرة واحدة. يزيل خيار المشغّل الاختياري <code>--reprocess-all</code> تصفية نافذة الاستقبال مع الحفاظ على قواعد التعارض والمراجعة. يشمل التاريخ المتاح فقط ولا يُنشئ سجلات غير موجودة في المصادر.</p><p>ليس هو <code>--full-refresh</code> ولا يحذف العمل السابق. اترك <code>--include-correction</code> غير مفعّل في اليوم الثاني؛ فهذا الفحص الاختياري لمرحلة لاحقة. لا يوجد تسليم إضافي.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>7. Interpret freshness correctly</h2><p>The current classroom settings in <a href="dbt/models/sources.yml">sources.yml</a> warn after 24 hours and fail after 48 hours, using the actual <code>_ingested_at</code>. These are exercise settings, not an organizational SLA. Warnings remain visible; errors stop the phase. Do not replace old receipt timestamps with the current time to force success.</p><p>The runner invokes <code>dbt source freshness</code> separately before each build; <code>dbt build</code> does not include it automatically. [D2-7, D2-8]</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٧. فسّر حداثة المصدر بصورة صحيحة</h2><p>تحذّر إعدادات التمرين الحالية في <a href="dbt/models/sources.yml">sources.yml</a> بعد 24 ساعة، وتوقف الفحص بعد 48 ساعة، باستخدام <code>_ingested_at</code> الفعلي. هذه إعدادات تمرين وليست اتفاق مستوى خدمة لجهة. تبقى التحذيرات ظاهرة وتوقف الأخطاء المرحلة. لا تستبدل توقيتات الاستقبال القديمة بالوقت الحالي للحصول على نجاح صوري.</p><p>يستدعي المشغّل <code>dbt source freshness</code> بصورة منفصلة قبل كل بناء؛ لا يتضمنه <code>dbt build</code> تلقائيًا. تاريخ الرحلة التاريخي ليس وقت وصولها. عند استئناف مدخلات قديمة، احتفظ بها واستخدم مساحة يوم أول جديدة لمحاولة متكاملة حديثة. [D2-7، D2-8]</p></td></tr></table>
