<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>1. A Delta table is more than Parquet files</h2><p>Parquet holds columnar data. The Delta transaction log identifies the committed table state and its metadata. After an update, old files may still exist. Read the table with the Delta reader; collecting every Parquet file can include obsolete data. Do not edit <code>_delta_log</code> manually. [D1]</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>١. جدول Delta ليس ملفات Parquet فقط</h2><p>تحفظ Parquet البيانات عموديًا. ويحدد سجل معاملات Delta حالة الجدول المعتمدة وبياناته الوصفية. قد تبقى ملفات قديمة بعد التحديث؛ لذلك اقرأ الجدول بقارئ Delta. قد يؤدي جمع كل ملفات Parquet إلى إدراج بيانات قديمة لم تعد ضمن الحالة الحالية. لا تعدّل <code>_delta_log</code> يدويًا. [D1]</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>2. Give ACID a practical meaning</h2><p><strong>Atomicity:</strong> a table write commits as a unit.<br><strong>Consistency:</strong> defined constraints must hold.<br><strong>Isolation:</strong> concurrent access follows snapshot and conflict rules.<br><strong>Durability:</strong> committed state persists under the storage system’s guarantees.</p><p>In 04a, a single append with a valid row and a negative-fare row is rejected without partially changing the constrained copy. This tests that operation, not every ACID property under load. Separate table writes do not become one multi-table transaction. [D2, D3]</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٢. اربط ACID بمعنى عملي</h2><p><strong>الذرّية:</strong> تعتمد كتابة الجدول كوحدة واحدة.<br><strong>الاتساق:</strong> يجب تحقق القيود المعرّفة.<br><strong>العزل:</strong> يخضع الوصول المتزامن لقواعد اللقطات والتعارض.<br><strong>الديمومة:</strong> تبقى الحالة المعتمدة وفق ضمانات نظام التخزين.</p><p>في 04a تُرفض كتابة تحتوي صفًا صحيحًا وآخر بأجرة سالبة دون تعديل جزئي للنسخة ذات القيد. يختبر ذلك العملية المحددة، لا جميع خصائص ACID تحت الضغط. ولا تتحول الكتابات على جداول منفصلة إلى معاملة واحدة متعددة الجداول. [D2، D3]</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>3. Separate source revision from table version</h2><p><code>source_revision</code> orders corrections to a particular trip. A Delta table version identifies a committed state of the whole table. Source revision 2 is not necessarily table version 2. Read the actual version from history. The scenario assigns revision 2 to the correction; the original CSV has no revision column.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٣. افصل مراجعة المصدر عن نسخة الجدول</h2><p>يرتب <code>source_revision</code> تصحيحات رحلة محددة. أما رقم نسخة Delta فيحدد حالة معتمدة للجدول كله. مراجعة المصدر 2 ليست بالضرورة نسخة الجدول 2. اقرأ رقم النسخة الفعلي من السجل. يمنح السيناريو التصحيح مراجعة رقم 2؛ ولا يحتوي CSV الأصلي على عمود للمراجعة.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>4. Decide which revision wins</h2><p>Use an explicit application policy: a valid missing key is inserted; a higher revision updates an existing key; identical revision and content leave values unchanged; an older revision is ignored; equal revisions with different content stop processing. Receiving the old SAR 18.00 value later must not erase the approved SAR 23.00 correction. These rules are defined in <a href="CHANGE_POLICY.md">this lab’s change policy</a>, not inferred automatically by Delta.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٤. حدد أي مراجعة تُعتمد</h2><p>استخدم سياسة تطبيق صريحة: يُضاف المفتاح الصحيح غير الموجود؛ وتُحدّث المراجعة الأعلى مفتاحًا موجودًا؛ وتبقى القيم عند تطابق المراجعة والمحتوى؛ وتُتجاهل المراجعة الأقدم؛ ويتوقف التنفيذ عند تساوي المراجعات واختلاف المحتوى. وصول الأجرة القديمة 18.00 لاحقًا لا يلغي التصحيح المعتمد 23.00. يحددها <a href="CHANGE_POLICY.md">دليل تغيير اللاب</a>، ولا تستنتجها Delta تلقائيًا.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>5. MERGE is not append</h2><p>Match on <code>trip_id</code> and update only when <code>s.source_revision &gt; t.source_revision</code>. Validate source and target uniqueness first: several source rows matching one target can make the update ambiguous. The supplied correction matches an existing trip, so the count remains 75. Trace <code>revision_merge_delta</code> in <a href="../src/masar/delta_lab.py">the shared code</a>; the notebook already calls it. MERGE ليس إلحاق الصفوف</h2><p>طابق على <code>trip_id</code>، وحدّث فقط عندما تكون <code>s.source_revision &gt; t.source_revision</code>. افحص تفرد مفاتيح المصدر والهدف أولًا؛ فقد تجعل صفوف مصدر متعددة للهدف نفسه التحديث غامضًا. يصحح الملف المرفق رحلة موجودة، لذلك يبقى العدد 75. تتبّع <code>revision_merge_delta</code> في <a href="../src/masar/delta_lab.py">الكود المشترك</a>؛ يستدعيها الدفتر بالفعل. <table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>6. Compare business contents when replaying</h2><p>Idempotency means that repeating the operation preserves its intended logical result. Compare sorted business rows or their canonical content hash. Correct runs may use different filenames, timestamps and transaction versions. A new history entry alone does not mean an extra trip was created.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٦. قارن محتوى الأعمال عند الإعادة</h2><p>تعني خاصية Idempotency أن تكرار العملية يحافظ على نتيجتها المنطقية المقصودة. قارن صفوف الأعمال المرتبة أو بصمة محتواها المعيارية. قد تختلف أسماء الملفات والتوقيتات ونسخ المعاملات بين تشغيلات صحيحة. لا يعني ظهور عملية جديدة في السجل وحده إضافة رحلة أخرى.</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>7. Schema and business quality are different</h2><p>A decimal fare can still be negative, and a string driver ID can still be unknown. Schema enforcement handles columns and types; constraints and explicit checks handle other rules. A declared business key is not automatically a uniqueness constraint in this setup. The lab uses <code>fare_sar IS NOT NULL AND fare_sar &gt;= 0</code> so null is not mistaken for a valid non-negative fare. [D3, D9]</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٧. المخطط وجودة الأعمال مختلفان</h2><p>قد تكون الأجرة عشرية لكنها سالبة، وقد يكون معرف السائق نصًا لكنه مجهولًا. يضبط فرض المخطط الأعمدة والأنواع، وتغطي القيود والفحوص الصريحة القواعد الأخرى. إعلان مفتاح أعمال لا يفرض تفرده تلقائيًا في هذا الإعداد. يستخدم اللاب <code>fare_sar IS NOT NULL AND fare_sar &gt;= 0</code> حتى لا تُقبل القيمة الفارغة بوصفها أجرة صحيحة غير سالبة. [D3، D9]</p></td></tr></table>

<table dir="ltr" width="100%"><tr><td width="50%" dir="ltr" lang="en" align="left" valign="top"><h2>8. Files staged during a failed write are not evidence of committed rows.</p></td><td width="50%" dir="rtl" lang="ar" align="right" valign="top"><h2>٨. يحتاج الرفض المتوقع إلى دليل محدد</h2><p>ينجح الاختبار السلبي فقط عند حدوث رفض القيد أو المخطط المقصود وثبات الصفوف والمخطط ونسخة الجدول المعتمدة. غياب مكتبة أو انقطاع عملية Spark خطأ مختلف. الملفات التي قد تُجهز أثناء كتابة فاشلة ليست دليلًا على صفوف معتمدة.</p></td></tr></table>
